# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 Cross(+) 패턴과 X 패턴을 판별하는 Python 콘솔 시뮬레이터이다.
외부 라이브러리 없이 표준 라이브러리(`json`, `time`, `os`)만 사용했다.

## 실행 방법

```bash
python main.py
```

- Python 3.8 이상 필요
- `data.json`은 `main.py`와 같은 폴더에 위치
- 실행 후 모드 선택
  - `1`: 사용자 입력(3x3). 필터 A, B와 패턴을 한 줄씩 공백으로 구분해 입력
  - `2`: data.json 분석. 5x5, 13x13, 25x25 필터와 패턴을 일괄 판정
  - `3`: [보너스] 2D 배열과 1D 배열의 MAC 성능 비교

모드 1 입력 예시(십자가 필터 / X 필터 / X 패턴):

```
0 1 0      1 0 1      1 0 1
1 1 1      0 1 0      0 1 0
0 1 0      1 0 1      1 0 1
```

결과: A 점수 1.0, B 점수 5.0, 판정 B

## 구현 요약

- **데이터 구조**: NxN 2차원 리스트(`list[list[float]]`)로 패턴과 필터를 저장했다. 특정 위치의 값은 `matrix[i][j]`로 읽고 쓴다. 저장은 `input_3x3_matrix()`(모드 1 입력)와 `generate_patterns()`(패턴 생성)에서, 읽기는 `mac_2d()`의 위치별 곱셈에서 이루어진다. 3x3부터 25x25(보너스 벤치마크는 50x50)까지 처리한다.
- **MAC 연산**: `mac_2d()`가 이중 반복문으로 같은 위치의 값끼리 곱해 누적한다. NumPy 등은 사용하지 않았다.
- **라벨 정규화**: `normalize_label()`이 expected(`+` → Cross, `x` → X)와 필터 키(`cross` → Cross, `x` → X)를 표준 라벨 `Cross`/`X`로 통일한다. 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준이다.
- **모듈화(함수 분리 이유)**: 라벨 정규화를 `normalize_label()` 하나로 분리했다. expected 값과 필터 키 두 곳에서 같은 규칙을 써야 하므로, 규칙을 한 곳에만 두면 두 입력이 항상 같은 기준으로 표준화된다. 새 표기(예: `CROSS`, ` x `)를 허용하거나 라벨을 추가할 때도 이 함수만 고치면 되고, 함수 단독으로 입력→출력을 확인할 수 있어 테스트가 쉽다. 같은 이유로 MAC 연산(`mac_2d`), 판정(`judge_scores`), 행렬 검증(`validate_square_matrix`), 시간 측정(`measure_mac_performance`)도 각각 분리해 모드 1과 모드 2가 같은 함수를 재사용한다.
- **동점 정책(epsilon)**: `abs(score_a - score_b) < 1e-9`이면 동점으로 보고 `UNDECIDED`로 판정한다. 실제 누적 오차는 약 1e-15 수준이고 의미 있는 점수 차이는 0.1 이상이므로, 1e-9는 오차는 흡수하고 실제 차이는 구분할 수 있는 값이다.
- **검증**: 모드 1은 한 줄씩 입력받아 정상적인 줄이 3개 모일 때까지 반복하므로 행 수가 부족하거나 넘칠 수 없다. 각 줄에서는 열 개수 불일치, 숫자 파싱 실패, `nan`/`inf` 입력(`float()`가 숫자로 받아들이는 값) 시 안내 문구를 출력하고 해당 줄을 재입력받는다. 메뉴에서 1~3 이외의 값을 입력하면 다시 입력받고, 입력 중 `Ctrl+C`/EOF가 들어오면 오류 출력 없이 종료 메시지를 남기고 끝난다. 모드 2는 아래 오류가 있으면 해당 케이스만 FAIL로 처리하고 프로그램은 계속 진행한다.
  - 최상위·filters·patterns가 객체가 아닌 경우, 패턴 항목이 객체가 아닌 경우 (스키마 오류)
  - 키에서 N 추출 실패, 해당 크기 필터 누락, 행/열 크기 불일치, 숫자가 아닌 값 포함
  - expected가 `+`/`x` 등 정규화 가능한 값이 아닌 경우 (알 수 없는 라벨)
- **파일 경로**: `data.json`은 `main.py` 위치를 기준으로 찾으므로 다른 폴더에서 실행해도 동작한다.
- **모드 1 성능 분석**: 판정 후 3x3 크기의 평균 시간(ms)과 연산 횟수(9)를 표로 출력한다.
- **성능 측정**: 입출력과 파일 읽기를 제외하고 `mac_2d()` 호출 구간만 `time.perf_counter()`로 10회 반복해 평균(ms)을 구한다.
- **보너스**: `generate_patterns(n)`(Cross/X 자동 생성), `flatten_matrix()`와 `mac_1d()`(1차원 배열 최적화), 모드 3 비교 벤치마크를 구현했다.

### 2. 실패 원인 분석

전체 6개 케이스 중 3개(size_5_1, size_13_2, size_25_1)가 FAIL이었다. 세 건 모두 Cross 점수와 X 점수의 차이가 epsilon(1e-9) 미만이라 `UNDECIDED`로 판정되었고, 이는 expected와 일치할 수 없으므로 FAIL로 집계되었다. 원인을 데이터/스키마, 로직, 수치 비교의 세 갈래로 분리해 진단했다.

1. **데이터/스키마 문제: 아니다.** expected(`+`, `x`)와 필터 키(`cross`, `x`)를 표준 라벨 `Cross`/`X`로 정규화한 뒤 비교하므로 라벨 불일치로 인한 FAIL은 없었다. 정규화가 없었다면 `+` ≠ `Cross`가 되어 PASS인 케이스까지 FAIL이 되었을 것이다. 필터와 패턴의 크기 불일치도 없었다.
2. **로직 문제: 아니다.** 크기 검증, 필터 선택, MAC 연산은 정상 동작했다. 점수 차이가 뚜렷한 3건(size_5_2, size_13_1, size_25_2)은 PASS였다.
3. **수치 비교 문제와 데이터 설계: 이것이 원인이다.** 필터 가중치가 서로 달라 두 점수가 이론상 동일해지는 케이스가 포함되어 있었다.
   - size_5_1: X 필터의 가중치는 0.1이고 Cross 필터의 중앙값은 0.9이다. 완전한 X 패턴은 1이 9개이므로 X 점수는 9 x 0.1 = 0.9, Cross 점수는 중앙 한 칸의 0.9이다. 이론상 동점이며, 실제 계산값은 0.9와 0.8999999999999999였다.
   - size_13_2: 십자가 패턴의 1은 25개(13 + 13 − 1)이고 Cross 필터의 해당 칸은 모두 0.3이다. 따라서 Cross 점수는 0.3을 25번 누적한 값이며 이론값은 7.5이다. X 필터는 패턴과 중앙 한 칸에서만 겹치고 그 값이 7.5이므로 곱셈 한 번으로 7.5가 나온다. 0.3은 이진 부동소수점으로 정확히 표현되지 않아 25번 누적하는 동안 오차가 쌓였고, Cross 점수는 7.499999999999997이 되었다. 이론상 같은 값이 덧셈 횟수의 차이로 서로 다르게 계산된 것이다.
   - size_25_1: size_5_1과 같은 구조이다. 완전한 X 패턴의 1은 49개(25 + 25 − 1)이고 X 필터의 해당 칸은 모두 0.1이므로, X 점수는 0.1을 49번 누적한 값이며 이론값은 4.9이다. Cross 필터는 패턴과 중앙 한 칸에서만 겹치고 그 값이 4.9이므로 곱셈 한 번으로 정확히 4.9가 나온다. 0.1 역시 이진 부동소수점으로 정확히 표현되지 않아 누적 오차가 생겼고, X 점수는 4.899999999999999가 되었다. size_13_2와는 오차가 쌓인 쪽이 반대(Cross가 아니라 X)이다.

**epsilon 정책의 효과.** 두 점수의 차이가 1e-9 미만이면 동점으로 간주하는 정책을 적용했다. 부동소수점 오차는 1e-15~1e-16 수준이라 epsilon보다 훨씬 작으므로 동점으로 안전하게 처리되었다. 이 정책이 없었다면 size_13_2에서 7.5 > 7.499999999999997이라는 이유로 X로 판정되어, 실제 Cross 패턴을 오판했을 것이다.

**개선 방향.** 필터를 정규화(합이 같도록 스케일링)하거나 가중치를 달리 설계해 점수 간격을 벌리면 동점을 줄일 수 있다. 다만 본 과제의 규칙은 동점을 판정 불가로 두는 것이므로 현재 구현을 유지했다.

**결론.** FAIL 3건은 코드 오류가 아니라, 데이터상 이론적으로 동점인 케이스를 epsilon 정책이 올바르게 `UNDECIDED`로 처리한 결과이다.

**의도적 오류 입력 테스트.** 스키마 방어가 실제로 동작하는지 확인하려고 data.json을 복사해 잘못된 케이스를 넣고 실행했다. 모든 경우 프로그램은 종료되지 않았고 케이스 단위로 FAIL과 사유가 출력되었다.

| 넣은 오류 | 출력된 실패 사유 | 분류 |

| 5x5 키에 2x2 input | 크기/데이터 불일치 - 행 개수 불일치 | 데이터/스키마 |
| size_7 (필터 없음) | size_7에 해당하는 Cross/X 필터 누락 | 데이터/스키마 |

### 3. 성능 분석 (평균 / 10회)

측정값은 실행마다 달라진다. data.json에는 3x3 데이터가 없으므로, 3x3은 패턴 생성기 `generate_patterns(3)`로 만든 Cross/X 패턴으로 측정했다(보너스 2의 생성 패턴을 성능 분석에 재활용).

| 크기 | 평균 시간(ms) | 연산 횟수(N²) |
|---|---|---|
| 3x3 | 0.0030 | 9 |
| 5x5 | 0.0059 | 25 |
| 13x13 | 0.0271 | 169 |
| 25x25 | 0.0890 | 625 |

### 4. 시간 복잡도 분석

1. `mac_2d()`는 N개 행과 N개 열을 이중 반복문으로 순회하며 곱셈과 덧셈을 수행하므로 연산 횟수는 N²이다. 시간 복잡도는 **O(N²)**이다.
2. 3x3(9회)에서 25x25(625회)로 가면 연산 횟수는 약 69배 늘었고, 측정 시간은 0.0030ms에서 0.0890ms로 약 30배 늘었다.
3. 시간이 연산 횟수에 정확히 비례하지 않은 것은 함수 호출과 변수 초기화 같은 고정 비용이 작은 크기에서 큰 비중을 차지하기 때문이다. 크기가 커질수록 N²에 가까운 증가를 보였다. 13x13에서 25x25로 갈 때 연산 횟수는 약 3.7배(169 → 625), 시간은 약 3.3배로 비슷한 비율이었다.
4. 필터가 2개이고 패턴이 여러 개이면 전체 비용은 (패턴 수 x 2 x N²)이며, 입력 크기에 대해서는 여전히 O(N²)이다.
5. 실제 AI 모델은 수백x수백 크기의 필터를 수천 개 사용하므로 MAC 연산이 수억 번에 이른다. 순차 처리 방식의 CPU로는 부담이 커서 병렬 처리에 특화된 NPU가 필요하다.

### 5. 보너스: 2D 배열과 1D 배열 비교 (1000회 평균)

| 크기 | 2D (ms) | 1D (ms) | 개선율 |
|---|---|---|---|
| 3x3 | 0.00299 | 0.00183 | 38.9% |
| 5x5 | 0.00666 | 0.00344 | 48.3% |
| 13x13 | 0.02924 | 0.01815 | 37.9% |
| 25x25 | 0.08508 | 0.07034 | 17.3% |
| 50x50 | 0.33159 | 0.29408 | 11.3% |

1차원으로 평탄화하면 `matrix[i][j]`의 이중 인덱싱이 `flat[idx]` 한 번으로 줄어 반복 접근 비용이 감소한다. 두 방식 모두 연산 횟수는 N²으로 같아 복잡도는 바뀌지 않고 상수 계수만 개선된다. 같은 벤치마크를 5회 반복 실행한 결과, 1D가 2D보다 느린 경우는 없었으나 일부 크기(예: 13x13)에서는 차이가 거의 없는 때도 있었다. 다만 개선율은 실행마다 크게 달랐다(3x3은 약 44~50%로 안정적이었고, 25x25는 약 12~31%, 50x50은 약 2~25%). 큰 크기에서 개선율이 작고 흔들리는 경향은 보였으나(평탄화는 측정 구간 밖에서 미리 수행), 정확한 원인은 검증하지 않았다. 위 표는 그중 한 번의 측정값이다.

### 6. 새 라벨 확장 절차

현재 표준 라벨은 `Cross`, `X` 두 개다. 예를 들어 원(`Circle`) 패턴을 추가한다면 아래 순서로 수정한다.

1. **정규화**: `normalize_label()`에 `o`, `circle` → `Circle` 매핑 추가
2. **필터 로드**: 필터 로드 완료 조건 `len(normalized_filters[n]) == 2`와 패턴 분석의 `"Cross"`/`"X"` 존재 검사를 표준 라벨 목록 상수(예: `STANDARD_LABELS = ("Cross", "X", "Circle")`)를 기준으로 바꾼다.
3. **판정**: `judge_scores()`는 두 점수만 비교하므로, 모든 필터 점수 중 최댓값을 고르고 1위와 2위의 차이가 epsilon 미만이면 `UNDECIDED`로 판정하도록 일반화한다.
4. **출력**: 라벨 목록을 순회하며 라벨별 점수 출력
5. **테스트**: data.json에 Circle 필터와 케이스를 추가해 모드 2에서 PASS 확인


### 7. 대규모(N ≥ 1000) 처리 한계와 최적화

본 구현으로 큰 크기를 직접 측정했다(`generate_patterns()`로 만든 Cross/X 패턴, 3회 평균).

| 크기 | 연산 횟수(N²) | 2D MAC 1회(ms) | 1D MAC 1회(ms) |
|---|---|---|---|
| 100x100 | 10,000 | 0.3 | 0.3 |
| 500x500 | 250,000 | 9.5 | 8.1 |
| 1000x1000 | 1,000,000 | 41.7 | 33.6 |

- **시간**: 25x25(625회, 약 0.025ms)에서 1000x1000(100만 회)으로 연산 횟수가 1600배 늘었고, 시간도 약 1600배(약 40ms)로 늘어 O(N²)에 맞게 증가했다. 패턴 1개당 필터 2개를 계산하므로 약 80ms, 10회 반복 측정까지 하면 크기 하나에 약 0.8초가 걸린다. 패턴이 수천 개가 되면 순차 처리만으로는 수 분 단위가 된다.
- **메모리**: 파이썬 리스트는 원소마다 8바이트 참조를 갖고, 값이 서로 다른 실수라면 float 객체(24바이트)가 추가되어 원소당 약 32바이트가 든다. 1000x1000 행렬 하나가 약 32MB이고, 패턴과 필터 2개를 동시에 들고 있으면 약 100MB가 된다. 또한 `json.load()`는 파일 전체를 한 번에 메모리에 올리므로 데이터가 커질수록 로드 시간과 메모리가 함께 늘어난다.
- **병목**: 곱셈 자체보다 큰 행렬의 값을 메모리에서 읽어오는 비용(메모리 대역폭, 캐시 미스)과 파이썬 인터프리터의 반복 오버헤드가 크다.

우선 적용할 최적화(효과가 큰 순서):

1. **0 건너뛰기(희소 처리)**: Cross/X 패턴은 대부분 0이다. 1000x1000 X 패턴에서 1인 칸은 1,999개뿐이므로 0이 아닌 위치만 저장해 곱하면 연산이 약 500분의 1로 줄어든다.
2. **1D 평탄화 + 필터 재사용**: 측정상 1000x1000에서 1D가 약 20% 빨랐다(41.7 → 33.6ms). 필터는 한 번만 평탄화해 모든 패턴에 재사용한다.
3. **블록(타일) 처리**: 행렬을 작은 블록 단위로 나눠 읽고 계산하면 캐시 적중률이 올라가고, 파일도 블록 단위로 나눠 읽으면 전체를 메모리에 올리지 않아도 된다.
4. **병렬 처리**: 패턴끼리는 서로 독립이므로 표준 라이브러리 `multiprocessing`으로 여러 패턴을 동시에 계산할 수 있다. 이것이 NPU가 수천 개의 MAC을 병렬로 처리하는 원리와 같다.
